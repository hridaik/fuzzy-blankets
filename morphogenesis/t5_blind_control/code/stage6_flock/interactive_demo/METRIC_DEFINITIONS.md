# METRIC_DEFINITIONS.md

Precise definitions for every metric shown in the interactive demo, and
exactly how each is computed from the real simulator data — no value in the
demo is inferred from visual appearance or invented per-run. This
complements the concise in-app "Methods & Metrics" panel with full formulas
and provenance. All code referenced lives in
`interactive_demo/data/export_scenarios.py`.

## Scope note: trajectory-level vs. ensemble-level

Every number here is one of exactly two kinds, and the demo never mixes
them into one unlabeled figure:

- **Trajectory-level** (`bundle.summary`): computed from the ONE continuous
  stochastic realization shown in the animation (the flock's own discovery
  seed, continued through control and release).
- **Ensemble-level** (`bundle.ensemble`): a cross-reference to a genuinely
  matching, already-frozen replicated result in `v3_refinement/data/*.json`
  or `v2_interface_control/data/*.json`. Attached **only** when a real
  per-flock condition matches (exactly or by closest actuator count, always
  labeled which); left `available: false` otherwise. No ensemble number is
  ever fabricated or approximated by rerunning a small ad hoc sample at
  demo-build time.

## Control-cost and timing metrics (new in this refinement pass)

### Peak concurrent actuator cost, `k_max`

$$ k_{\max} = \max_t |A_t| $$

`max(metrics.n_actuators_t)`. Every scenario in this demo uses a fixed
actuator set for the whole control window (no staged schedules are shown
here — see `v3_refinement/RESULTS_V3.md` Part 2D for the staged-actuation
science), so in practice `k_max = |A|`, the actuator count itself. The
metric is still computed generically from the per-timestep array, not
hard-coded to `|A|`, so a future staged-schedule bundle would compute
correctly without code changes.

### Total actuator exposure, `C_bird-step`

$$ C_{\text{bird-step}} = \sum_t |A_t| $$

`sum(metrics.n_actuators_t)`. For a fixed `k`-actuator pulse over `T_u=20`
steps, this is exactly `k * 20`.

### Actual override count, `C_override`

$$ C_{\text{override}} = \sum_{t,k} \mathbf{1}[u^{\text{applied}}_{k,t} \neq u^{\text{natural}}_{k,t}] $$

**How this was obtained**: `flock_sim.active_inference.step` already computes
`natural_action` (what the bird would have chosen on its own), `applied_action`
(what actually happened, after any forced override), and `was_overridden`
(their pointwise inequality) at every timestep, for every bird — this is
existing, validated simulator output (see `tests/test_active_inference.py`).
V1/V2/V3's exporters simply never saved these arrays to a JSON bundle. This
refinement's `export_scenarios.py` **reruns the identical simulation**
(same seed, same lattice, same intervention dictionary) to additionally
capture `natural_action_hist` / `applied_action_hist` / `overridden_hist`.
Because the whole simulation is a pure function of `(seed, lattice,
interventions)` via a single `numpy.random.Generator` stream (no global RNG
state), this rerun produces **bit-identical** `headings`/`trajectory` output
to a run that discarded these arrays — verified by
`interactive_demo/data/verify_bundles.py`, which recomputes every summary
statistic (including `override_count`) directly from the stored raw arrays
and confirms an exact match against the embedded `summary` block for all 30
bundles. **This is not a new scientific experiment or a re-tuned trajectory
— it is the same frozen protocol, rerun once to log an already-computed
diagnostic that was previously thrown away.** `override_count` is available
for every bundle in this demo (all were generated by the current exporter);
no bundle marks it "unavailable."

### Time to target, `t_hit`

The **frozen scientific success definition is unchanged**: `H*(t0+T_u) >= 0.8`,
an endpoint check (`summary.success`, `summary.Hstar_at_control_end`).

No dwell rule was ever defined for `H*` in V1/V2/V3 (only the endpoint was
used). Per the task brief's own instruction ("if no dwell was previously
defined for target success... display a clearly labelled exploratory
'first threshold crossing' without silently changing the scientific success
definition"), this demo adds **two exploratory, clearly-separate**
diagnostics, neither of which redefines `summary.success`:

$$ t_{\text{hit,dwell}} = \min\{t \in [\text{control\_start}, \text{release\_end}] : H^\star(t{:}t+2) \ge 0.8\} $$

using `dwell=3`, borrowed from V3's own recovery-dwell constant (chosen for
consistency with an already-frozen quantity rather than inventing a new
arbitrary number) — `summary.time_to_target_dwell3` (relative to control
start) and `summary.time_to_target_dwell3_abs` (absolute timestep). This is
what the UI labels "Target reached" and "Time to target."

$$ t_{\text{hit,first}} = \min\{t : H^\star(t) \ge 0.8\} $$

a plain first-crossing with no dwell — `summary.time_to_target_first_crossing`
— shown in the app's raw data for completeness but not surfaced as a
headline number, since a single noisy crossing is a weaker claim than a
sustained one.

### Coherence recovery time, `t_recovery`

Using V3's own transition-aware integrity definition
(`v3_refinement/PROTOCOL_V3.md`, `integrity_v3`): `C_recover=0.8`,
`dwell=3` consecutive steps, searched within the control window:

$$ t_{\text{recovery}} = \min\{t \in [\text{control\_start}, \text{release\_end}] : C_{I_0}(t{:}t+2) \ge 0.8\} $$

`summary.recovery_time` (relative to control start) and
`summary.recovery_time_abs`. `null` if never achieved within the window.

### Release persistence

`summary.persistent = H*(release_end) >= 0.5` — the frozen persistence bar,
unchanged from V1/V2/V3. `summary.final_post_release_Hstar` is the raw
value shown alongside the Yes/No.

## Redundant support metrics

### Mean multiplicity

$$ \bar m(A) = \frac{1}{|I_0|}\sum_{i \in I_0} m_i(A), \qquad m_i(A) = |\{j \in A : j \sim i\}| $$

`summary.mean_multiplicity`, via `coverage_metrics.multiplicity_summary`
(unchanged from `v3_refinement/`, imported not reimplemented). **V3's
strongest single predictor of control success** — see
`v3_refinement/RESULTS_V3.md` Part 1.

### Double-covered fraction

$$ \Gamma_2(A) = \frac{|\{i \in I_0 : m_i(A) \ge 2\}|}{|I_0|} $$

`summary.gamma2` (static, for the fixed actuator set) and
`metrics.double_coverage` (per-timestep, 0 outside the control window). This
is the quantity the frozen V3 controller (`sparse_interface_multicover`)
directly optimizes (`gamma=0.5` target — see `v3_refinement/PROTOCOL_V3.md`).
Shown **more prominently** than plain `Gamma` in the sidebar, per the UX
brief, with `Gamma` demoted to the expandable "More metrics" section and
explicitly labeled as a weaker predictor.

### Binary coverage (retained, explained as insufficient)

$$ \Gamma(A) = \frac{|\{i \in I_0 : m_i(A) \ge 1\}|}{|I_0|} $$

`summary.gamma`, `metrics.coverage`. V3 found this the **weakest** of the
structural predictors tested (McFadden R² 0.379, vs. 0.610 for `mean_m`) —
see `v3_refinement/RESULTS_V3.md` Part 1A/1C — because it saturates almost
immediately as the actuator budget grows and then has nothing left to say
in exactly the range where success keeps improving. Retained and explained,
never hidden.

## Pre-existing metrics (unchanged definitions, carried over from V1/V2/V3)

- **Target fraction** `H*(t) = mean_{i in I0}[z_i(t) == h*]` — `flock_sim.metrics.target_heading_fraction`.
- **Core coherence** `C(t) = max_h mean_{i in I0}[z_i(t) == h]` — `flock_sim.metrics.coherence`.
- **Frozen core** `I0`, **dynamical shell** `B^D`, **Fiedler boundary** `B^F`
  — unchanged definitions from `v1_mechanism_audit/` / `v2_interface_control/`.

## What was NOT changed

No V1/V2/V3 protocol, threshold, simulator code, or frozen conclusion was
modified to produce any of the above. `t_hit` and `t_recovery`'s dwell rule
reuses `dwell=3` exactly because it is already a frozen V3 constant, applied
here to a second quantity (`H*`) it was not originally defined for — this
reuse is stated plainly above, not silently presented as if it had always
applied to target-fraction hitting time.

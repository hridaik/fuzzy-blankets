# Stage 6.8 / 6.9 visualization notes

The 6th `Inference & Identity` tab, **Dynamic Interfaces**, with two internal
views: **6.8 Dynamic flock** and **6.9 Translation pilot**. This was a
visualization pass only. No scientific analysis was re-run, no Stage 6–6.9
result file was modified, and no conclusion here is new — everything shown is
either copied verbatim from a frozen result file or regenerated by a
deterministic replay that is asserted equal to one.

Scope check: one new sub-tab, no new top-level navigation item (`#topNav` still
has exactly the three buttons it had before, and the Playwright suite asserts
that). Sizing and layout reuse `.iiMain` / `.iiGraphCol` / `.iiSideCol` /
`.iiCard` / `.iiStat` unchanged, so the Control tab remains the reference.

---

## 1. Representative-trajectory selection rule

One rule, **R1**, applied identically to every representative choice in both
stages:

> Given the candidate episodes and a list of reported metrics, take the median
> of each metric across candidates and score each episode by
>
>     score = Σ_m |x_m − median_m| / MAD_m
>
> (MAD = median absolute deviation; a metric with zero spread contributes 0).
> Choose the minimum score. Ties break to the lowest seed id.

This selects the episode nearest the middle of the reported distribution. It is
not a visual choice — the selection code never sees a rendering, and the full
ranked table (every candidate, its score, its metrics) is shown in each view's
**Details** panel so the choice is auditable in the page itself.

| view | candidate pool | metrics used | chosen |
|---|---|---|---|
| L0 | `oracle_interface.json`, label `L0_fixed_graph` (6 seeds) | mean \|B\|, mean symdiff, mean turnover, distinct interfaces | seed 15 |
| L2 | same file, label `L2_fov`, **restricted to seeds that also have stored inference results** (15, 17) | mean \|B\|, mean symdiff, mean turnover, node lifetime, distinct interfaces | seed 15 |
| L3 | `oracle_reveal__gated.json` (6 seeds) | \|B^D\|, J(causal, B^D), \|B̂^pred\|, \|B̂^causal\| | seed 22 |
| control | `control.json`, seeds with all six arms present | the six arms' `final_target_fraction` (as a 6-vector) | seed 192 |
| 6.9 spec | `translation_gate__R0.9_v0.28.json`, tracked episodes (40) | R_M, R_F, component count, D_deform | seed 37 |
| 6.9 off-spec | `translation_gate__R1.6_v0.5__SUPERSEDED.json`, **gate-passing only** | same four | seed 6 |

The L2 restriction matters and is not cosmetic: the overlays only mean anything
if the episode has stored `B̂^pred` / `B̂^causal`, so the pool is restricted to
episodes that have them rather than picking a median episode and then leaving
the overlay controls dead.

## 2. Data provenance, and what had to be replayed

**Copied verbatim from frozen files** — every interface set, every metric:
`oracle_interface.json`, `boundary_inference__{series,gated}.json`,
`oracle_reveal__{series,gated}.json`, `control.json`, `gate_choice.json`,
`boundary_inference__snapshot.json`, and both Stage 6.9 gate files.

**Regenerated by deterministic replay** — per-timestep headings, the live-edge
state, the latent L3 gate, and the control arms' state trajectories. The science
runs never persisted these (they stored interfaces and metrics, not the raw
`z_hist`). They are recovered by re-running the frozen simulator at the same
seed and configuration, which is deterministic, and **every replayed quantity is
asserted against the frozen file it must match**:

- L0 and L2: the replayed `B_t^D` must equal `oracle_interface.json`'s
  `B_series` at all 61 timesteps;
- L2's inference window: the replayed `B_t^D` for each stored interior must
  equal `oracle_reveal__series.json`'s recorded `B_D`;
- L3: same against `oracle_reveal__gated.json`;
- control: each replayed arm's `final_target_fraction` must equal
  `control.json`'s to 1e-12 — all six arms, exact;
- Stage 6.9: the re-derived track's `R_M` and size must equal the frozen gate
  record frame by frame.

A replay that drifted would fail the export, not silently feed the demo a
different trajectory. Generators:
`stage6_8_dynamic_interactions/code/export_demo_data_68.py` and
`stage6_9_translating_collective/code/export_demo_data_69.py`; bundles
`data/stage6_8_bundle.json` (381 KB) and `data/stage6_9_bundle.json` (1.8 MB),
inlined by `app/build.py` like every other bundle. `file://` operation and the
no-server setup are unchanged.

## 3. What the 6.8 view shows

One 20×20 lattice (nn = 400, the Stage 6.8 operating point), real heading
arrows on every bird, play/pause/step/slider, and a four-way condition
selector: **L0 fixed graph · L2 FOV · L3 FOV + gates · Control**.

`drawIILattice` gained two optional parameters (`radius`, `arrowScale`) whose
defaults reproduce the previous values exactly, so tabs 1–5 render unchanged;
Stage 6.8 uses smaller dots and longer arrows because 400 birds at the old
radius hid the heading arrows inside the dots.

**Interior selector — and a correctness constraint that shaped it.** Two modes,
*Fixed reference I* and *Tracked collective I(t)*, and the second is only
enabled where a real per-timestep track was stored (L0 and L3 used a fixed
interior, so the button is disabled there with a tooltip saying why).

The tracked collective shown is **the one the stored inference results were
computed for** — the series pipeline's own tracked lineage over t = 55–66 — not
`detection.json`'s largest per-step candidate. Those two are *disjoint*
(Jaccard 0.00 at every timestep in the window: 92-bird vs 130-bird communities).
Pairing the boundaries with the larger set would have drawn `B̂^pred` and
`B̂^causal` around a group they do not belong to. Consequently:

- in **Fixed reference** mode only that disc's oracle `B_t^D` exists, so the
  predictive and sampled-causal overlays are *disabled*, with a line saying
  where they do exist;
- in **Tracked collective** mode the timeline restricts to t = 55–66, and all
  overlays apply to exactly the interior on screen.

**Membership turnover** is marked subtly in tracked mode: members that
*remained* stay the core blue, birds that *entered* this step are teal, birds
that *left* keep an outlined teal ring on the exterior fill. Legend entries
appear only in that mode.

**Overlays**, all off by default: inferred predictive boundary · sampled causal
interface · oracle causal interface `B^D` · live directed interactions for a
selected bird. The two oracle-derived toggles are tinted with the `--warn`
colour. The live-interaction overlay is a lookup, not a simulation: the bundle
carries the static neighbour and slot lists, the 8×4 FOV visibility table and
(L3 only) the per-frame gate bitmask, and the client resolves the selected
bird's live in-edges from its stored heading.

**Metrics beside the lattice**, and only these: `|I_t|`, material retention,
`|B_t^D|`, predictive-boundary size, sampled-causal size, and — only when the
oracle overlay is on — `J(causal, B^D)` and `J(predictive, B^D)`. Everything
else (selection table, provenance, full numbers) is under **Details**.

**Control view**: one representative episode, all six arms from the same
starting condition (`no control · predictive · matched random · frozen causal ·
adaptive inferred · adaptive oracle`), actuated nodes drawn directly on the
lattice, and a compact target-fraction trace with every arm faint and the
selected arm highlighted. The caveat is carried in one line, verbatim:
*The oracle task was not reliably feasible at this collective size.*

## 4. What the 6.9 view shows

Two synchronized panels — **World frame** and **Co-moving frame** — driven by a
single frame index, so they cannot desynchronize. The world panel shows every
bird plus the detected collective; the co-moving panel shows the same
collective after the estimated bulk translation is removed, using the stored
collective-centred coordinates the identity calculation itself uses.

**The default is the specified model** (`R = 0.9`), whose gate failed 0/40.
Metrics beside the panels are only: `R_M`, `R_F`, spatial component count,
`D_deform`, path travelled, and `|I_t|`. `R_F` and the component count are
coloured against their gate thresholds, so the failure reads off the panel
without depending on the caption: the world panel shows the "collective"
scattered into disconnected clumps and the co-moving panel shows a diffuse
cloud rather than a persistent pattern.

**Off-spec diagnostic** (`R = 1.6`) is selectable but never the default. It
carries a persistent warning strip — *Off-spec diagnostic — not a Stage 6.9
result* — that is present the whole time the view is open, not a dismissible
banner. It exists because the contrast is what identifies connectivity as the
controlling variable: the same layout and the same six metrics show `R_M`
falling while `R_F` stays high, which is what a coherent translating
organization looks like.

## 5. What is deliberately NOT shown

- **No Stage 6.9 guidance/control visualization.** The valid protocol stopped
  at the feasibility gate, so there is no steering result to show.
- **No superseded oracle guidance probe.** The off-spec `(K_act, horizon)`
  feasibility grid is not visualized; presenting it would imply it was part of
  the stage.
- **No tracked-interior mode for L0 or L3.** Those experiments used a fixed
  interior; a time-varying one is not manufactured to fill the control.
- **No inference overlays outside their own collective or their own window.**
- **No new dashboard.** Six live metrics per view; everything else in Details.
- **No re-derivation in JavaScript.** The client decodes stored strings and
  bitmasks and does set lookups; it never advances a dynamics.
